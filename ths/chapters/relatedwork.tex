\chapter{Related Work}
\label{ch:relatedwork}

The rollup literature covers formal security analysis and mainnet throughput under normal load. It rarely tests both architectures under the same adverse conditions with the same instrumentation. This chapter reviews what exists, identifies where it stops, and explains what this framework contributes.

\section{Academic Research on Layer~2 Protocols}

\subsection{Systematisation of Knowledge}

Thibault et al.\ provide a comprehensive systematisation of Layer~2 blockchain protocols~\cite{sok-layer2}. Their taxonomy organises the design space into four families. Payment channels, exemplified by the Lightning Network and Raiden, enable bidirectional off-chain transfers between fixed pairs of participants. Sidechains, including Plasma and various commit-chain designs, operate as semi-independent chains that periodically anchor their state to the parent chain. Rollups, encompassing both ZK and Optimistic variants, post transaction data on-chain while moving execution off-chain. Hybrid approaches such as Validium and Volition blend on-chain and off-chain data availability to offer a configurable trade-off between cost and security.

The systematisation provides a useful taxonomy and analyses security properties at a theoretical level. What it does not include is any empirical measurement of how these systems behave under failure conditions. The absence of controlled experiments leaves open whether the theoretical security guarantees hold under real failure conditions.

\subsection{ZK Rollup Research}

Bünz et al.\ introduced Bulletproofs, a proof system that generates efficient zero-knowledge range proofs without a trusted setup ceremony~\cite{zk-efficient-proofs}. By eliminating that ceremony, Bulletproofs removed a significant barrier to deploying zero-knowledge schemes in decentralised settings. Subsequent work extended this toward SNARKs capable of verifying general computation---the foundation for ZK~Rollups over arbitrary smart contract logic.

The zkSync documentation describes a ZK~Rollup design focused on proof generation and EVM compatibility~\cite{zksync-paper}. The Scroll project~\cite{scroll2023} describes an on-chain verifier based on a SNARK proof. The \texttt{ZKVerifier} contract in this thesis takes its structural pattern from these designs: a submission function that requires a proof and a finalisation check tied to block confirmation. We compress the confirmation delay to five blocks and replace the BN254 pairing check with a hash comparison, so the framework does not require specialised hardware.

Neither of these bodies of work measures ZK~Rollup behaviour when something breaks---no systematic data exists on finality under Layer~1 reorganisations or sequencer outages. That is the gap this thesis addresses.

\subsection{Optimistic Rollup Research}

Kalodner et al.\ introduced Arbitrum, one of the first Optimistic~Rollups~\cite{arbitrum-original}. Their main contribution is the interactive fault game: a multi-round dispute protocol that narrows disagreement to a single instruction, which the Layer~1 contract re-executes to settle the dispute. This avoids re-executing the whole batch on-chain.

The \texttt{OptimisticVerifier} contract in this thesis borrows two specific patterns from Arbitrum Nitro~\cite{nitro2023} and Optimism Bedrock~\cite{optimism2023bedrock}: the configurable challenge window and the four-state commitment lifecycle (\texttt{PENDING}, \texttt{SOFT\_FINAL}, \texttt{HARD\_FINAL}, \texttt{CHALLENGED}). The difference is that our dispute resolution is simplified to a binary outcome---any \texttt{challenge()} call invalidates the root---rather than the full interactive bisection game. This preserves the property we care about for comparison (incorrect roots can be blocked before finality) without the implementation complexity that production systems require.

Kalodner et al.\ discuss sequencer liveness, but the cost of failure recovery has not been measured in a controlled setting. That is one of the four gaps this thesis addresses.

\subsection{Arbitrum}

Arbitrum is a widely deployed Optimistic~Rollup on Ethereum mainnet~\cite{nitro2023}. It uses a seven-day challenge window and an interactive fraud proof mechanism based on the Arbitrum Virtual Machine. Optimism uses Cannon as its fault proof virtual machine~\cite{cannon2023}. If the centralised sequencer goes offline, a decentralised validator set can take over transaction ordering.

This is directly relevant to the design in Chapter~\ref{ch:implementation}: the ten-block challenge window and the binary challenge outcome in \texttt{OptimisticVerifier} are simplified versions of the Arbitrum model. The simplification removes the multi-round bisection game but keeps the property needed for comparison---an incorrect state root can be blocked before it becomes final.

\subsection{Optimism}

Optimism introduced the OP Stack, a modular framework that lets other teams deploy rollup chains sharing the same security model~\cite{opstack2023}. Its Bedrock upgrade defines a staged withdrawal lifecycle: pending, soft-final while the challenge window is open, and hard-final once the window closes without a dispute or the withdrawal is explicitly finalised.

The \texttt{OptimisticVerifier} contract in this thesis takes this lifecycle model directly from Bedrock. The four states (\texttt{PENDING}, \texttt{SOFT\_FINAL}, \texttt{HARD\_FINAL}, \texttt{CHALLENGED}) let the dashboard and test suite observe transitions between stages. They make the finality rule visible in the contracts; they do not produce a wall-clock latency measurement in Chapter~\ref{ch:evaluation}.

\subsection{zkSync and StarkNet}
\label{sec:zk-production}

zkSync targets EVM compatibility with validity proofs~\cite{zksync-paper}. StarkNet uses the Cairo language with a STARK proof system~\cite{starknet2024,cairo2021}. STARKs scale efficiently for large computations and require no trusted setup, though they produce larger proof objects than SNARKs. Both projects have spent years optimising proof generation on specialised hardware.

The \texttt{ZKVerifier} contract in this framework follows the submission-plus-confirmation model from zkSync Era (see Figure~\ref{fig:impl-repos}): a \texttt{submit()} function that requires a proof object and a finalisation check gated on block confirmation count. The proof generation step in the ZK sequencer simplifies the zkSync design by replacing BN254 elliptic-curve pairings with a domain-separated keccak mock proof, so the evaluation does not require specialist hardware. Neither zkSync nor StarkNet publishes data on sequencer downtime or failure recovery, which is one of the gaps this thesis addresses.

\subsection{OpenZeppelin Contracts}

The \texttt{OptimisticVerifier} and \texttt{ZKVerifier} contracts follow the access-control and event-emission patterns established in the OpenZeppelin Contracts library~\cite{openzeppelin2024}. Specifically, ownable ownership checks on the \texttt{submit()} function and the use of indexed events for off-chain monitoring are taken directly from OpenZeppelin's standard patterns. Using an audited pattern rather than writing custom access control reduces the surface area for correctness errors in the framework's L1 layer.

\section{Gap Analysis and Thesis Contribution}

Reading across this literature, four areas come up repeatedly where empirical data is missing. The framework addresses all four directly.

\textbf{Finality rule under testbed conditions.} The literature describes the finality properties of both rollup families, but it does not compare them under the same conditions. The framework records the submission block and the block at which each contract's rule is satisfied. The result in Chapter~\ref{ch:evaluation} is a rule difference: the ZK path waits five L1 blocks after proof acceptance and the Optimistic path waits a ten-block challenge window. No wall-clock finality is measured in Hardhat, and the production gap follows from assumed protocol parameters.

\textbf{Loss set after RPC failure.} When the RPC connection drops during batch assembly, the sequencer loses the accepted but unconfirmed set. The controlled comparison records that loss set and checks Layer~1 state integrity; it does not measure restart time. The results show that both sequencers preserve Layer~1 state while losing the pending set. The Optimistic path loses more transactions because its larger batch threshold holds them longer.

\textbf{Controlled comparison.} Existing benchmarks evaluate a single rollup architecture in isolation, making comparison difficult because environmental conditions differ. Running both sequencers against the same Layer~1 node simultaneously, with identical block timing and gas pricing, is the core design choice that makes the results in Chapter~\ref{ch:evaluation} directly comparable.

\textbf{Reproducibility.} Existing performance data for Layer~2 systems comes from mainnet observations or proprietary benchmarks that others cannot replicate. This framework is open-source and deployable with one command. Another researcher can verify every number in Chapter~\ref{ch:evaluation} or run the same scenarios with different parameters.

\section{Where the Existing Literature Leaves Off}

Existing work is either production systems optimised for normal execution or academic papers analysing theoretical properties. What is missing is a direct comparison of both approaches under the same conditions, with the same instrumentation, under adversarial scenarios. This framework addresses that gap.
Chapter~\ref{ch:framework} describes the design choices that make a controlled comparison possible. Chapter~\ref{ch:implementation} covers the code.
