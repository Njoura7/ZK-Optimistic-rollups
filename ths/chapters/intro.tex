\chapter{Introduction}
\label{ch:intro}

\section{The Problem}

Bitcoin~\cite{nakamoto2008bitcoin} solved a specific problem: two strangers can exchange value without a bank. Ethereum~\cite{wood2014ethereum} generalised that idea to programmable computation. Both networks hit the same wall. Bitcoin processes around 7 transactions per second. Ethereum manages roughly 15. Visa handles thousands per second. That gap matters because fees spike under demand and most real applications cannot use the network reliably.

The reason is structural, not accidental. Every node must validate every transaction. That keeps the network secure and decentralised, but it is slow. Making it faster without giving something up is not straightforward.

Layer~2 systems try a different route. Instead of validating every transaction on-chain, Layer~1 validates a summary---a single commitment representing thousands of transactions processed in a batch. The commitment is what anchors Layer~2 security to Layer~1. If the commitment is wrong, Layer~1 rejects it. If it is correct, the batch is settled.

Two approaches to building that commitment emerged. ZK~Rollups compute a cryptographic proof that the commitment is valid and submit it alongside the state root. Layer~1 checks the proof immediately and finalises the batch. Optimistic~Rollups skip the proof. They post the state root and open a window during which anyone can dispute it. If no valid challenge arrives before the window closes, the commitment becomes final.

Which is better? It depends on what you care about. ZK~Rollups finalise faster but proof generation is expensive. Optimistic~Rollups cost less but users wait days for settlement in production. The more honest answer is that we have good theoretical descriptions of both and limited empirical data on how they behave when conditions are not ideal.

\section{What Is Missing}

Academic papers describe the theory well. Production systems demonstrate that both approaches can reach useful scale. But the literature is quiet on what actually happens when things break.

When Layer~1 undergoes a chain reorganisation---and it does happen---which finality model is more resilient? When a sequencer crashes or disconnects, what can users do and what does recovery cost? When a commitment turns out to be wrong, how does each system catch and handle it?

These are not edge cases invented for a thesis. Sequencer outages have occurred on live networks. Chain reorganisations are a routine part of how Ethereum works at short depths. Yet there is remarkably little published work that measures ZK versus Optimistic behaviour under these conditions with direct comparison.

The dominant pattern in existing evaluations is to measure throughput when the network is uncongested, latency when sequencers are working, and costs under ideal load. That is useful, but it tests the path that is least likely to go wrong.

\section{What This Thesis Does}

This thesis builds a testing framework and runs both rollup types through it---under normal operation and deliberate failures---to characterise when each approach is the better choice.

The framework puts both sequencers against the same Hardhat Layer~1 node. We simulate sequencer crashes. We submit invalid state roots. We observe what each architecture does. For each scenario, we record finality latency, recovery behaviour, and whether transactions are lost. The two key findings: ZK achieves true finality around 8~times faster than Optimistic in the demo environment, and that advantage widens dramatically in production because the Optimistic challenge window is 7~days rather than 10~blocks. The cost trade-off runs the other way---Optimistic uses roughly 3~times less Layer~1 gas per transaction because it batches more aggressively and skips proof calldata.

Everything is open-source and starts with one Docker command. The goal is that another researcher can reproduce the experiments, check the numbers, and extend the evaluation to configurations we did not test.

\section{Research Questions}

The evaluation tackles four questions.

First, how long does a transaction actually take to become irreversible? Theory says ZK~Rollups finalise in seconds and Optimistic~Rollups take days in production. What do we measure in a controlled environment, and does the ratio hold?

Second, when a sequencer crashes, what is the cost of recovery? Do pending transactions survive? How long before the system is processing again?

Third, what are the real trade-offs between the two approaches? ZK computes proofs; Optimistic waits. Where do the costs actually land---in computation, in gas, in time?

Fourth, is a fair comparison achievable on standard developer hardware? If yes, the framework is useful to other researchers. If no, it is only a toy.

\section{Why a Framework Rather Than Mainnet Measurement?}

One obvious alternative is to run both systems on Ethereum mainnet and compare them directly. The problem is environmental noise. Gas prices shift. Network conditions change. Different sequencer implementations make different engineering choices in dozens of small ways. Any difference you observe might come from the architecture or from everything else. A controlled framework isolates what matters.

Another alternative is formal analysis alone. The limitation there is that real systems diverge from models. Proof generation latency depends on batch size, hardware, and implementation choices that formal analysis does not capture. Fraud proofs require network propagation that models assume away. Real bugs appear in deployed code. Formal analysis gives bounds; measurement gives data about actual systems.

The framework is not a replacement for either. It sits between them---more empirical than formal analysis, more controlled than mainnet measurement.

\section{Contributions}

Three concrete things come out of this work. First, an open-source framework that runs both sequencer types against the same Layer~1 node, with configurable batch sizes, polling intervals, and gas allocations. Anyone can clone it, adjust a parameter, and re-run the comparison. Second, measured data on finality latency, recovery cost, and proof overhead for both architectures under identical conditions, including the adversarial scenarios that most evaluations skip. Third, an interface specification in the repository documentation so a researcher can implement a new sequencer type---say a hybrid or a different proof system---and plug it into the same contracts and metrics infrastructure.
