\chapter{Introduction}
\label{ch:intro}

\section{The Problem}

Bitcoin~\cite{nakamoto2008bitcoin} solved a specific problem: two strangers can exchange value without a bank. Ethereum~\cite{wood2014ethereum} generalised that idea to programmable computation. Both networks face the same ceiling: Bitcoin processes around 7 transactions per second, Ethereum around 15, while traditional payment networks handle thousands~\cite{croman2016scaling}. The gap is structural---every node validates every transaction, which keeps the network secure but limits throughput.

Layer~2 systems address this by moving execution off-chain. A sequencer batches transactions, computes a state commitment, and posts it to Layer~1. Layer~1 only validates the commitment, not each transaction individually. Two approaches to this commitment emerged. ZK~Rollups attach a cryptographic proof; Layer~1 verifies it immediately and finalises the batch. Optimistic~Rollups post only the state root and open a window during which anyone can dispute it; if no challenge arrives, the commitment becomes final.

ZK~Rollups finalise faster; Optimistic~Rollups cost less. Both are described well in theory, but empirical data on how they behave when conditions are not ideal is limited.

\section{Motivation}

My field of study is service and software architecture, so distributed systems is a core subject. My supervisor pointed me to the textbook by van Steen and Tanenbaum~\cite{vansteen2023distributed}, which covers blockchain as a hybrid distributed architecture (Chapter~2) and fault tolerance mechanisms (Chapter~8). The book is a solid foundation but it does not address Layer~2 protocols or how different rollup designs compare under failure conditions.

That gap became the starting point. I was curious about blockchain from a systems perspective---not just the theory but what real implementations do under real conditions. A friend working as a blockchain developer pushed the question further: he pointed out that most Layer~1 scalability problems are addressed and that the active research gaps are now at Layer~2, particularly around rollup behaviour under failures. That conversation shaped the scope of this thesis.

\section{Research Gap}

Academic papers on Layer~2 protocols cover security proofs and normal-case throughput. Production deployments demonstrate scale. What neither provides is empirical data on failure behaviour: how each architecture responds to sequencer crashes, invalid state submissions, and chain reorganisations, and how the two compare under the same conditions.

Existing evaluations measure throughput under ideal load, latency when sequencers are working, and cost in uncongested conditions. That covers the path least likely to go wrong. Sequencer outages have occurred on live networks; chain reorganisations are routine at short depths. Yet no published work measures ZK and Optimistic behaviour side by side under these conditions with reproducible methodology.

\section{Research Questions}

\begin{enumerate}
    \item How does finality latency differ between the two architectures under identical Layer~1 conditions, and does the theoretical gap hold in practice?
    \item What is the cost of sequencer crash recovery---in time, pending transaction loss, and Layer~1 state integrity?
    \item Where do the real trade-offs land: proof overhead and throughput?
    \item Can a reproducible head-to-head comparison be achieved on standard developer hardware?
\end{enumerate}

\section{Innovation and Contributions}

We built a controlled testbed where both rollup architectures run against the same local Ethereum node~\cite{hardhat2024} under identical conditions, including deliberate failures. We simulate sequencer crashes, submit invalid state roots, and record what each design does. The headline result: ZK achieves true finality around 8~times faster than Optimistic in this environment, and the gap grows to roughly 672~times compared to a production seven-day challenge window.

Three things make this different from existing work. It is the first controlled head-to-head comparison of both rollup types under adversarial conditions on the same node---existing benchmarks test one architecture in isolation. Every result is reproducible: the testbed starts with one Docker command and produces the same output on any machine. And adding a third rollup type requires only a new Solidity contract and a Python class that follows the existing interface.

One scope note: gas figures in Chapter~\ref{ch:evaluation} are EVM gas units returned by Hardhat through transaction receipts. They reflect real opcode costs and allow direct comparison between ZK and Optimistic submissions. They cannot be converted to ETH or dollar amounts without a gas price that this local environment does not have, so only relative differences are reported.

\section{Thesis Structure}

Chapter~\ref{ch:background} covers the technical background: why blockchains are slow by design and how ZK and Optimistic rollups address that differently. Each section maps the theory directly to the code built in this thesis.

Chapter~\ref{ch:relatedwork} surveys existing work and shows where it stops, which is where this thesis begins.
