\chapter{Background: Layer~2 Scaling Solutions}
\label{ch:background}

Blockchain throughput is limited by design, not accident. This chapter traces why, then shows how the ZK and Optimistic responses to that constraint appear in the code built for this thesis.

% -----------------------------------------
\section{Blockchain Fundamentals}
\label{sec:fundamentals}
% -----------------------------------------

Bitcoin~\cite{nakamoto2008bitcoin} established a decentralised consensus model for exchanging value without intermediaries. Ethereum extended it with a programmable execution layer~\cite{wood2014ethereum}. Both networks face a hard throughput ceiling: Bitcoin sustains roughly seven transactions per second and Ethereum around fifteen, both governed by block-level resource limits~\cite{croman2016scaling}. From a distributed systems perspective, a blockchain is a specific instance of a replicated state machine~\cite{vansteen2023distributed}---one designed for adversarial settings where participants cannot be assumed to trust each other.

A blockchain can be modelled as a state machine. At each block~$t$ the network holds a global state~$S_t$; incoming transactions produce a successor:
\begin{equation}
  S_{t+1} = \text{apply}(S_t,\ \text{txs}_t)
\end{equation}
Integrity rests on three properties~\cite{vansteen2023distributed}: consensus (agreement on transaction ordering), finality (irreversibility of confirmed blocks), and data availability (full auditability by any participant). Layer~2 systems inherit these properties from the base layer rather than building them independently. The commitment posted to Layer~1 is the mechanism through which that inheritance is anchored.

% -----------------------------------------
\section{The Layer~2 Execution Model}
\label{sec:l2concept}
% -----------------------------------------

Layer~2 systems separate execution from settlement~\cite{gudgeon2020sok}. A sequencer orders transactions, executes them off-chain, and periodically submits a state commitment to a Layer~1 smart contract. Security derives from that on-chain commitment, not from the off-chain environment.

The economic motivation is cost amortisation. One Layer~1 verification is shared across an entire batch:
\begin{equation}
  \text{Cost per L2 tx} =
    \frac{\text{L1 batch cost} + \text{L2 execution cost}}{\text{batch size}}
\end{equation}
The two dominant rollup families differ in what the sequencer submits alongside the state root: a cryptographic validity proof in the ZK case, or nothing---relying instead on a post-hoc fraud challenge---in the Optimistic case~\cite{sok-layer2}. In this thesis, gas consumption is measured as EVM gas units reported by the Hardhat node. These reflect opcode costs and allow a relative comparison between architectures, but they do not correspond to ETH or dollar amounts because Hardhat uses a fixed gas price rather than a market-derived one.

\section{ZK Rollups}
\label{sec:zk}
% -----------------------------------------

A ZK~Rollup requires a validity proof with every state commitment~\cite{sok-layer2}. The prover computes a zk-SNARK attesting that the transition from $\text{state}_\text{old}$ to $\text{state}_\text{new}$ is correct:
\begin{equation}
  \pi = \text{Prove}(\text{state}_\text{old},\ \text{txs},\ \text{state}_\text{new})
\end{equation}
The Layer~1 verifier contract accepts or rejects the submission immediately based on the proof alone---no waiting period is needed~\cite{sok-layer2}. Production systems use several proof systems, including Groth16, PLONK, and STARKs~\cite{groth2016size,gabizon2019plonk,bensasson2018stark}; the framework replaces the verifier with a mock.

\textbf{Security.}
Safety follows from proof soundness: a dishonest sequencer cannot produce a valid proof for an incorrect state transition. In this framework finality follows the proof plus five L1 blocks (Chapter~\ref{ch:evaluation}); production parameters differ.

\textbf{Constraints.}
Proof generation is computationally expensive, and pairing-based verification costs more than a hash comparison~\cite{groth2016size}. The mock proof avoids that cost, so its timing is not a production cost estimate. PLONK~\cite{gabizon2019plonk} and STARKs~\cite{bensasson2018stark} change different parts of that overhead.

\textbf{Framework instantiation.}
Both sequencers compute the same batch commitment with \texttt{l2\_common.commitment.batch\_merkle\_root}: a keccak256 binary Merkle root over ABI-encoded \texttt{(from,to,value)} tuples. It is not a post-execution state trie root. \texttt{ZKVerifier.sol} accepts it together with a 32-byte mock proof (a domain-separated keccak hash from \texttt{mock\_proof()}) and binds them to a placeholder verifying-key hash; there is no circuit or pairing check. This preserves the structural property (proof required at submission; no challenge window) without the hardware cost of real elliptic-curve computation. Batch size and polling interval default to 100~transactions and 5~seconds.

\section{Optimistic Rollups}
\label{sec:optimistic}
% -----------------------------------------

An Optimistic~Rollup posts a state root without a proof and opens a challenge window---a period during which any observer can dispute the commitment by submitting a fraud proof~\cite{arbitrum-original}. In production deployments such as Optimism and Arbitrum, this window is seven days. In this framework it is compressed to ten Layer~1 blocks for experimental tractability. Hardhat mines only on transactions, so the window has no fixed wall-clock duration.

Fraud proving in production systems uses a bisection protocol that narrows disagreement to a single instruction, which Layer~1 re-executes~\cite{arbitrum-original}.

A commitment that survives its window without a valid challenge transitions from optimistic acceptance to finality. The \texttt{OptimisticVerifier.sol} contract in this framework models the lifecycle through four states: \texttt{PENDING}, \texttt{SOFT\_FINAL}, \texttt{HARD\_FINAL}, and \texttt{CHALLENGED}.

\textbf{Security.}
Safety depends on the condition that at least one honest watcher monitors the chain: the system is secure as long as one participant challenges invalid roots within the window~\cite{arbitrum-original}. This is an economic guarantee enforced through sequencer collateral, not a cryptographic one~\cite{sok-layer2}.

\textbf{Constraints.}
The challenge window is the primary usability cost: withdrawals to Layer~1 are delayed by the full window unless a liquidity provider offers early exit for a fee. Full transaction data must be published on-chain so watchers can reconstruct state independently; EIP-4844 blob transactions~\cite{eip4844} reduce this data cost in recent deployments.

\textbf{Framework instantiation.}
\texttt{l2-optimistic/sequencer.py} submits the same batch commitment without proof generation; both sequencers call \texttt{l2\_common.commitment.batch\_merkle\_root} on ABI-encoded \texttt{(from,to,value)} tuples. Batch size and polling interval default to 200~transactions and 8~seconds. Both sequencers load and cache the verifier contract handle once, with a retry on the next batch if deployment was still pending. Recovery scenarios are triggered programmatically and observed through Prometheus metrics on their respective ports (9100 for ZK, 9101 for Optimistic).

Both rollup families move execution off-chain and anchor security on-chain, but differ in the mechanism that links the two: immediate cryptographic verification in the ZK case versus deferred economic enforcement in the Optimistic case. That design choice underlies the finality rule and invalid-submission handling. The remaining differences come from configuration: batch thresholds drive crash loss, and the on-chain commitment struct drives the small gas difference. Table~\ref{tab:bg-summary} puts the two side by side. The gas row describes production designs; in this testbed both submissions are close, and the Optimistic path is slightly more expensive because its commitment struct is larger (Chapter~\ref{ch:evaluation}).
