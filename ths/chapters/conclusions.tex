\chapter{Conclusions and Future Work}
\label{ch:conclusion}

The four research questions have bounded answers. One comes from protocol rules and three from the committed harness. ZK and Optimistic rollups differ in their finality rules and in their crash-loss windows, and the comparison is reproducible on a standard laptop. The framework keeps the ZK proof as a mock and compresses the challenge window to ten blocks, so it answers questions about structure and determinism, not about real proving cost or production finality latency.

\section{What We Found}

The finality gap is the main result, and it is architectural rather than measured. The ZK rule accepts a proof plus five L1 blocks; the Optimistic rule waits a ten-block challenge window in the demo (about seven days in production). Assuming roughly 15~seconds for ZK gives an assumed production ratio of about 40,320 to one. Both the 15-second and seven-day values are protocol-parameter assumptions, not framework measurements. The difference follows directly from the design: one architecture requires a proof before accepting a batch, the other waits to see if anyone objects.

Batch configuration and gas tell a more balanced story. The ZK path uses a 100-transaction threshold and submits more often; the Optimistic path uses a 200-transaction threshold and submits less often. Per-submission gas is close on Hardhat, and no multi-batch total is reported. Throughput is not compared because the TPS gauges reflect the injection loop. Crash loss was symmetric in kind but not in scale: both sequencers preserved Layer~1 state integrity and lost their in-memory pool, with Optimistic losing 200 transactions against 100 for ZK because of its larger threshold.

Neither architecture dominates across the reported dimensions. The choice depends on what the application cannot afford to compromise: withdrawal latency favours ZK, while fewer L1 submissions favour Optimistic.

\section{What This Work Contributes}

The contribution is a testing environment that runs both sequencer types against the same Layer~1 node under identical conditions, including deliberate failures. Its results are tied to a pinned golden vector and a committed raw artefact, so anyone can verify the commitment and crash-loss figures after starting the stack with one command. The sequencer interface specifies what a new architecture must implement to plug into the existing contracts and metrics stack.

\section{Limitations}

Two limitations are structural. The ZK proof in the framework is a mock proof based on a domain-separated keccak hash (about 0.008\,ms at P95), not a SNARK. It plays the structural role of a proof---submission is gated on it---but it contributes nothing meaningful to the overhead figures. Real Groth16 proving is not measured here; adding it is documented future work in \texttt{docs/PATH\_B\_GROTH16.md} and is not part of this thesis. The Hardhat environment adds a second layer of simplification: deterministic blocks, zero network latency, no mempool congestion. These choices make a controlled comparison possible, but the absolute numbers are not portable to a deployed system without adjustment.

\section{Future Work}

The most direct extension is connecting the same stack to a public testnet. Sepolia and Holesky both provide free test ETH from faucets and real network conditions without mainnet costs. Stochastic block times and variable gas prices would replace the conditions this setup controls away, and the finality rule could then be measured as a wall-clock latency without rewriting the framework code.

A second direction is cloud deployment. The stack is already packaged into a single Docker compose file. Running that on a cloud instance rather than a local machine would make the framework accessible to researchers without the hardware to run a local Ethereum node alongside two sequencers and a monitoring stack simultaneously. It would also allow longer experiments and larger transaction volumes than a laptop can sustain. It also changes the research workflow: a collaborator receives a running instance instead of cloning the repository and reproducing the environment locally. This makes external checks easier to arrange.

Adding a third architecture---a Validium variant, or a hybrid that uses ZK proofs for finality but Optimistic data posting---requires a new sequencer, contract, Compose service, scrape configuration, dashboard panels, and tests. The existing metrics schema can then be reused.

The main gap this thesis cannot close is the measured cost of real ZK proof generation. Replacing the mock with a real Groth16 prover on even a single batch would provide that lower bound without changing anything else about the framework.

\section{Practical Relevance}

Withdrawal latency and bridge design are practical constraints on applications. The seven-day withdrawal window is not only a specification detail; it shapes which applications can be built on an optimistic rollup.

The framework does not resolve that constraint. It makes the trade-off explicit through an instrumented and reproducible setup.
