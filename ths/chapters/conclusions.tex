\chapter{Conclusions and Future Work}
\label{ch:conclusion}

The four research questions have bounded answers. Two come from protocol rules and two from a committed harness. ZK and Optimistic rollups differ in their finality rules and in their crash-loss windows, and the comparison is reproducible on a standard laptop. The framework keeps the ZK proof as a mock and compresses the challenge window to ten blocks, so it answers questions about structure and determinism, not about real proving cost or production finality latency.

\section{What We Found}

The finality gap is the headline result, and it is architectural rather than measured. The ZK rule accepts a proof plus five L1 blocks; the Optimistic rule waits a ten-block challenge window in the demo (about seven days in production). Assuming roughly 15~seconds for ZK gives an assumed production ratio of about 40,320 to one. Both the 15-second and seven-day values are protocol-parameter assumptions, not framework measurements. The difference follows directly from the design: one architecture requires a proof before accepting a batch, the other waits to see if anyone objects.

Batch configuration and gas tell a more balanced story. The ZK path uses a 100-transaction threshold and submits more often; the Optimistic path uses a 200-transaction threshold and submits less often. Per-submission gas is close on Hardhat, and no multi-batch total is reported. Throughput is not compared because the TPS gauges reflect the injection loop. Crash loss was symmetric in kind but not in scale: both sequencers preserved Layer~1 state integrity and lost their in-memory pool, with Optimistic losing 200 transactions against 100 for ZK because of its larger threshold.

The practical reading is not that one architecture wins. The choice depends on what the application cannot afford to compromise: if withdrawal latency is critical, ZK; if fewer L1 submissions matter more, Optimistic.

\section{What This Work Contributes}

The contribution is a testing environment that runs both sequencer types against the same Layer~1 node under identical conditions, including deliberate failures. Its results are tied to a pinned golden vector and a committed raw artefact, so anyone can verify the commitment and crash-loss figures after starting the stack with one command. The sequencer interface specifies what a new architecture must implement to plug into the existing contracts and metrics stack.

That last point shapes what comes next.

\section{Limitations Worth Naming}

Two limitations are structural. The ZK proof in the framework is a domain-separated keccak hash stand-in (about 0.008\,ms at P95), not a SNARK. It plays the structural role of a proof---submission is gated on it---but it contributes nothing meaningful to the overhead figures. Real Groth16 proving is far more expensive; adding it is documented future work in \texttt{docs/PATH\_B\_GROTH16.md} and is not part of this thesis. The Hardhat environment adds a second layer of simplification: deterministic blocks, zero network latency, no mempool congestion. These were the right trade-offs for a controlled comparison, but the absolute numbers are not portable to a deployed system without adjustment.

\section{Where This Framework Could Go}

The most direct extension is connecting the same stack to a public testnet. Sepolia and Holesky both provide free test ETH from faucets and real network conditions without mainnet costs. Stochastic block times and variable gas prices would replace the conditions this setup controls away, and the finality rule could then be measured as a wall-clock latency without rewriting the framework code.

A second direction is cloud deployment. The stack is already packaged into a single Docker compose file. Running that on a cloud instance rather than a local machine would make the framework accessible to researchers without the hardware to run a local Ethereum node alongside two sequencers and a monitoring stack simultaneously. It would also allow longer experiments and larger transaction volumes than a laptop can sustain. More importantly, it changes the research workflow: instead of asking a collaborator to clone a repository and reproduce the environment locally, you share a running instance. That is a meaningful difference for empirical research that is meant to be challenged and extended.

The sequencer interface is already built for this kind of extension. Adding a third architecture---a Validium variant, or a hybrid that uses ZK proofs for finality but Optimistic data posting---requires a new Solidity contract and a Python class that follows the existing pattern. The measurement infrastructure picks it up automatically.

The one gap this thesis cannot close is an honest ZK proof generation cost. Replacing the mock with a real Groth16 prover on even a single batch would provide that lower bound without changing anything else about the framework.

\section{Why This Problem Is Worth Studying}

The real motivation for studying this space is rarely theoretical. Anyone who has tried to move funds out of an L2 under time pressure, or bridge assets between ecosystems that were not designed to talk to each other, has already lived the experiment this thesis tries to instrument. The seven-day withdrawal window is not a specification detail. It is a constraint that shapes what applications can be built and who is willing to use them.

The framework does not resolve that tension. What it does is make the trade-off legible---instrumented, reproducible, and open to anyone who wants to test a different set of assumptions.
