\chapter{Conclusions and Future Work}
\label{ch:conclusion}

The two questions that shaped this thesis both have clear answers. ZK and Optimistic rollups differ meaningfully under controlled conditions, and the comparison can be done reproducibly on a standard laptop. What the experiments revealed is not just that the two architectures behave differently---theory already predicts that---but how consistently those differences appear even in a simplified framework where the ZK proof is mocked and the challenge window is compressed to ten blocks.

\section{What We Found}

The finality gap is the headline result. ZK achieves true finality around eight times faster than Optimistic in the demo environment; scaled to production parameters---seconds versus a seven-day challenge window---the ratio grows to roughly 672 to one. That is not a framework artefact. It follows directly from the design: one architecture requires a proof before accepting a state transition, the other waits to see if anyone objects.

Throughput and gas tell a more balanced story. ZK processes more transactions per second because its smaller batch threshold keeps the pipeline moving. Optimistic submits fewer batches and spends less total L1 gas for the same workload. Recovery from crashes was symmetric in kind but not in scale: both architectures preserved Layer~1 state integrity and both lost pending transactions, with Optimistic consistently losing more because its larger batch window lets more accumulate before being drained.

The practical reading is not that one architecture wins. The right choice depends on what the application cannot afford to compromise: if withdrawal latency is critical, ZK; if L1 cost matters more, Optimistic.

\section{What This Work Contributes}

Three things come out of this that did not exist before. A testing environment that runs both sequencer types against the same Layer~1 node simultaneously under identical conditions, including deliberate failures---so any comparison between the two is honest rather than circumstantial. A set of measured results on finality, gas cost, and recovery that anyone can verify by cloning the repository and running one command. And a sequencer interface specification that defines exactly what a new architecture must implement to plug into the existing contracts and metrics stack without touching what is already there.

That last point shapes what comes next.

\section{Limitations Worth Naming}

Two limitations are structural and worth stating plainly. The ZK proof in the framework is a double SHA-256 hash. It plays the structural role of a proof---submission is gated on it, finality follows immediately---but it contributes nothing meaningful to the overhead figures. Real Groth16 proof generation runs from several hundred milliseconds to minutes on production hardware. The Hardhat environment adds a second layer of simplification: deterministic blocks, zero network latency, no mempool congestion. These were the right trade-offs for a controlled comparison, but they mean the absolute numbers are not portable to a deployed system without adjustment.

\section{Where This Framework Could Go}

The most direct extension is connecting the same stack to a public testnet. Sepolia and Holesky both provide free test ETH from faucets and real network conditions without mainnet costs. That change alone would introduce stochastic block times and gas price variation that the current setup controls away, giving the finality measurements a second data point grounded in something closer to a real deployment---and it would not require rewriting any of the framework code.

A direction that feels more interesting to us is cloud deployment. The stack is already packaged into a single Docker compose file. Running that on a cloud instance rather than a local machine would make the framework accessible to researchers without the hardware to run a local Ethereum node alongside two sequencers and a monitoring stack simultaneously. It would also allow longer experiments and larger transaction volumes than a laptop can sustain. More importantly, it changes the research workflow: instead of asking a collaborator to clone a repository and reproduce the environment locally, you share a running instance. That is a meaningful difference for empirical research that is meant to be challenged and extended.

The sequencer interface is already built for this kind of extension. Adding a third architecture---a Validium variant, or a hybrid that uses ZK proofs for finality but Optimistic data posting---requires a new Solidity contract and a Python class that follows the existing pattern. The measurement infrastructure picks it up automatically.

The one gap this thesis cannot close is an honest ZK proof generation cost. Replacing the mock with a real Groth16 prover on even a single batch would provide that lower bound without changing anything else about the framework.

\section{Why This Problem Is Worth Studying}

The real motivation for studying this space is rarely theoretical. Anyone who has tried to move funds out of an L2 under time pressure, or bridge assets between ecosystems that were not designed to talk to each other, has already lived the experiment this thesis tries to instrument. The seven-day withdrawal window is not a specification detail. It is a constraint that shapes what applications can be built and who is willing to use them.

The framework does not resolve that tension. What it does is make the trade-off legible---measured, reproducible, and open to anyone who wants to test a different set of assumptions.
