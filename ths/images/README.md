## Reproducing the dashboard screenshots

The three figures under `dashboards/` are generated by
`capture_dashboards.js` in this directory. They were last regenerated after the
Grafana panels were renamed to "L1 Submission Latency" and the mock proof was
labelled explicitly.

### 1. Start the stack

From the repository root:

```bash
docker compose up --build -d
```

Wait for the services to answer before capturing:

| Service | URL | Notes |
|---------|-----|-------|
| Flask dashboard | `http://localhost:3000` | counters shown here |
| Grafana | `http://localhost:3001` | login `admin` / `admin` |
| Web3 demo | `http://localhost:3002` | MetaMask needed for live states |
| Hardhat L1 RPC | `http://localhost:8545` | mines on transactions only |
| ZK L2 API / metrics | `http://localhost:5000` / `:9100` | |
| Optimistic L2 API / metrics | `http://localhost:5001` / `:9101` | |
| Prometheus | `http://localhost:9090` | |

Grafana provisions its dashboard from
`config/grafana/dashboards/zk-optimistic-comparison.json` and reloads it every
10 seconds (`config/grafana/provisioning/dashboards/default.yml`), so panel
titles always match the committed JSON.

### 2. Inject representative traffic (optional but recommended)

Empty panels are still a valid capture, but counters and latency series are
more informative. Post directly to both sequencers, for example:

```python
import json, urllib.request
from concurrent.futures import ThreadPoolExecutor

def post(url, i):
    body = json.dumps({"from": f"user{i}", "to": f"user{i+1}", "value": 10}).encode()
    req = urllib.request.Request(url, data=body,
                                 headers={"Content-Type": "application/json"},
                                 method="POST")
    with urllib.request.urlopen(req, timeout=5) as r:
        return r.status

for port, n in [(5000, 500), (5001, 400)]:
    with ThreadPoolExecutor(max_workers=20) as ex:
        res = list(ex.map(lambda i: post(f"http://localhost:{port}/tx", i), range(n)))
    print(port, "posted", n, "statuses:", {s: res.count(s) for s in set(res)})
```

Check that the counters moved:

```bash
curl http://localhost:9100/metrics | findstr l2_transactions_total
curl http://localhost:9101/metrics | findstr opt_l2_transactions_total
```

### 3. Capture automatically

From `ths/images/`:

```bash
npm install --no-save playwright-core
node capture_dashboards.js --with-traffic
```

`BROWSER_PATH` can point at a local Chrome/Edge executable (the script defaults
to the Windows Edge path). `GRAFANA_URL` and `FLASK_URL` override the defaults.

The script logs in, verifies the eight corrected panel titles, and writes:

- `dashboards/grafana-top-panels.png` — 1920×570 clip: navigation, dashboard
  title, and the two stat rows (total transactions, batches, current TPS, and
  **L1 submission latency** for both paths).
- `dashboards/grafana-bottom-panels.png` — 1555×965 clip: transaction-rate
  comparison plus the four lower panels (mock proof generation time,
  optimistic batch processing time, pending transactions, gas per batch).
- `dashboards/flask-dashboard-overview.png` — full-page capture of the Flask
  dashboard; the script aborts if the "VALIDITY PROOF (MOCK IN TESTBED)" label
  is missing.

### 4. Capture manually (equivalent)

If you prefer the browser UI:

1. Open `http://localhost:3001`, log in with `admin` / `admin`, and select
   **ZK / Optimistic Rollup L2 Metrics Comparison**.
2. Keep the browser window at **1920×1080** with device scale factor 1.
3. For the top figure, screenshot the viewport and crop `(0, 0)–(1920, 570)`.
4. For the bottom figure, scroll **the dashboard's inner container** (not the
   page) to the end, then crop `(300, 110)–(1855, 1075)`. A normal "full page"
   screenshot will *not* work: Grafana scrolls internally at this viewport.
5. For the Flask figure, open `http://localhost:3000` and take a full-page
   screenshot once the counters have loaded.

Do not quote numbers from these images. The latency panels are sub-second
Hardhat submission-to-receipt measurements, not protocol finality.

## Reproducing the measurements

The numeric claims come from one committed artefact:

```bash
docker compose --profile test run --rm --workdir /app \
  test-runner python measurement/capture.py
```

This regenerates `measurement/raw/baseline-path-a.json`, which contains the
commitment and mock-proof timing percentiles and the crash-loss invariant. See
`measurement/README.md` for the full scope of what is and is not measured.
Re-run after changing the commitment or proof helpers; append a new campaign id
rather than overwriting an existing artefact.

## Abandoned capture plan (do not follow)

An earlier version of this file proposed figures that the data cannot support:

- Do **not** build a throughput bar chart from `l2_tps` / `opt_l2_tps`.
  Instantaneous TPS is dominated by the HTTP injection loop, not by the
  architecture. The former "39–43% advantage" claim was removed for lack of a
  raw artefact.
- Do **not** plot `*_finality_time_seconds_bucket` as a protocol-finality CDF.
  Those histograms record **L1 submission-to-receipt latency** (sub-second in
  Hardhat). They do not plateau at 15 s / 120 s, and 15 s / 7 days are protocol
  assumptions, not measurements. The Grafana panels were renamed to
  "L1 Submission Latency" accordingly.
